# FYP report supplement

Evidence review: 2 November 2026. This text supplements Academic Project II Chapters 3–7. It describes the current workspace integration separately from the October experiments. Evidence locations and qualifications are recorded in [RESEARCH-EVIDENCE.md](RESEARCH-EVIDENCE.md).

## Implementation update (Chapters 3–5)

Memoria now brings source review, maintained wiki pages, tracked temporal facts and optional meeting assistance into one workspace. The editor, vault and much of the desktop shell are inherited from Tolaria. The original FYP contribution is the decision ledger and its evaluation; the workspace adapters and review interfaces are later integration work. The historical report's statement that a wiki was replaced by a ledger describes an earlier design cycle. In the current application they coexist and have different responsibilities.

A source is the underlying document or saved, reviewed transcript. A compiled wiki page is a derived explanation, published after review with links and supporting quotes. A temporal fact is a typed claim about a declared item and attribute, held in a separate append-only ledger with valid time and recorded time. An approved wiki statement is not automatically a temporal fact. Live transcript turns and speaker labels remain provisional, including turns selected for checking after a newer turn arrives. They do not become approved memory merely because the system checks them.

The current `temporal_service.py` stores ledger state under `<workspace>/.memoria-memory/temporal/`. It requires a saved transcript, a declared tracked item and a parseable meeting date. Before extraction it checks that each recorded turn, timestamp label and speaker label still appears in the saved transcript. This is a consistency check, not full-document hash verification or proof that the supplied date is the actual meeting date. The adapter reuses the FYP prompt and parser through the shared local generator. Unlike the historical 7,000-character windowed path, `SharedExtractor` has no window wrapper. Long-transcript equivalence is therefore unverified.

Reviewed ingestion uses `confirm_all`. First values and later belief-changing candidates wait for human approval; non-changing confirmations follow the underlying policy's exception. This differs from the historical default, which reviewed conflicts but could apply first values directly. The current interface supports acceptance, rejection, correction with a reason, retraction and inspection of history. Editing a proposal before acceptance is available in the underlying service but is not exposed by the current panel.

Four deterministic lookup types remain available. The current panel selects an item, attribute and time perspective explicitly. The adapter excludes the model-based `ask` operation, so general wiki Ask must not be described as a natural-language temporal router. Change-count replies add history and evidence. The recorded-time form accepts one timestamp; it does not expose separate valid-time and transaction-time inputs. The setup interface also offers edits to existing definitions, while the preserved ledger refuses incompatible redefinitions. This interface mismatch needs resolution before full requirement conformance can be claimed.

The current `live_assistance.py` reads current ledger facts through a read-only SQLite snapshot. It excludes pending proposals and superseded fact rows, ranks facts by lexical overlap with their labels and attributes, and checks at most five. A direct numeric check applies only to an exact current equality with matching explicit unit or currency and a quote supporting the same equality. Other selected statements use one shared-generator verification call. A verdict must have the expected JSON fields and cite a selected fact; a conflict without the explicit tracked subject is suppressed. A cue contains the current value, quote, speaker, meeting and audio offset. The check cannot ingest or approve facts.

Live assistance is off by default in the HUD. When enabled, the HUD selects earlier transcript turns while leaving the newest turn unchecked, and retains at most three cues. This scheduling is implementation evidence, not a measured live service level. Lexical selection can miss aliases and paraphrases, semantic verification can be wrong, and a quiet result is not a correctness guarantee. The backend exposes warnings, but the HUD currently displays only selected status notices rather than all backend warnings. Read and worker deadlines are engineering limits, not latency measurements.

## Results and interpretation (Chapter 6)

The historical AMI temporal experiment answered 59 of 96 questions correctly when candidates were applied immediately, compared with 41/96 for full-context prompting and 37/96 for BM25 retrieval. An oracle reviewer raised the temporal result to 85/96. This is a scripted reviewer using gold knowledge, not observed human performance. A separate oracle-extractor ablation reached 96/96. It identifies extraction as the source of the observed answer errors on that dataset; it does not prove that routing is generally correct, since only 81/96 routes exactly matched the intended route.

All 29 AMI past-date answers were “nothing decided yet”, and 29 of 33 change-count answers were zero. The dataset contains four true value changes. It therefore provides a useful test of later decisions leaking into the past, but limited evidence for retrieving genuinely superseded values. Synthetic chains and the fictional series provide controlled revisions, with lower realism. Gold events and item definitions were derived with AI assistance from human abstracts, and questions were generated from templates. Oracle agreement checks consistency with the ledger, not independent human validity.

The separate MemoriaBench auditor reached macro-F1 0.87 on 336 generated statements from 28 AMI series. It received curated decision memory and replacement notes, rather than the current application's extracted facts and provisional speech. Only five of the 56 OUTDATED probes represent recorded replacements; 51 use synthetic replacement notes. Model-only label audits and template wording limit generalisation. This score measures the historical six-class auditor, not the current boolean live checker or the combined workspace pipeline.

The parent scratch verification ran the original deterministic engine suite: 291 discovered, run and passed, with no failures, errors or skips, in 4.319 seconds of unittest time. Before/after preservation checks covered 6,266 engine files, excluding the virtual environment. This supersedes the older 271-test snapshot as a current original-engine regression count; it does not revise historical coverage percentages. The parent supplied a separate snapshot of 37 new Python integration checks. Integration work is ongoing, so a fresh command and its output should be cited instead of a combined test total.

## Report corrections and outstanding evidence (Chapters 6–7)

The statement that all 37 frozen-manifest files still match is incorrect for the current original engine tree. A read-only checksum check found changes in `extractors.py`, `ledger.py`, `llmcache.py` and `pipeline.py`; all 14 manifest-listed data files still match, as do the remaining 19 code/script entries. Historical logs and the recorded offline replay support the earlier experiment and the effect of fixes. They do not make the present code identical to the frozen version.

The historical guard is also distinct from the current checker. Its documentation states that the alert threshold was selected after seeing both evaluation halves, so the reported guard figures are optimistic. The second-pass extraction filter has a separately documented threshold and sample. Neither filter's scores should be transferred to the workspace adapter. Exact quote matching establishes provenance, while citation-ID checking establishes reference identity; neither establishes that the claim follows from the quote. Human corrections may retain the earlier quote and require explicit explanation.

UAT remains pending in the report evidence reviewed. Remove wording implying that users have already evaluated or accepted the system, and do not describe planned participants as an observed sample. Clean-account task completion, current integrated native acceptance, live latency, long-meeting performance, combined model memory pressure and held-out end-to-end accuracy remain unverified. Historical post-recording WER/DER and isolated speech smoke measurements do not establish these outcomes. The current HUD saves audio chunks, so the old application's statement that audio is never written to disk must not be carried into the current implementation description.
